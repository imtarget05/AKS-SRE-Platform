**Why (measured, not guessed).** The `kubernetes/` root contains the repo's
legacy `ScaledObject/order-worker-scaler` (`kubernetes/keda-autoscaler.yaml`).
On 2026-10-20 that object applied cleanly, because at the time of the §2.3
measurement the `flashsale` Application had **not** yet been synced (§9 synced
it later the same day). After §9, the upstream application brought its **own**
`ScaledObject/order-worker` into the `flashsale` namespace, and KEDA creates
an HPA for it:

```console
flashsale   keda-hpa-order-worker   Deployment/order-worker   2/10 (avg)   1         4         1          9h
```

KEDA's admission webhook (`vscaledobject.kb.io`) refuses a second
`ScaledObject` for a workload that is already managed by one. So the **same
manifest** that validated 56/56 on 2026-10-20 validates 53/56 on 2026-10-21.

**How to state this claim so it stays true:**

> *Server-side dry-run of the 56 objects in the scope above, applied against
> `kind-local-platform` on 2026-10-20: 56 pass, 0 fail.*
> *Re-run on the same cluster on 2026-10-21 after the `flashsale` Application
> was synced: 53 pass, 3 fail — the 3 are the objects of the `kubernetes/`
> root, whose legacy `ScaledObject` is rejected by the KEDA admission
> webhook because the `flashsale` namespace already owns that workload.*

**The failure is therefore a statement about the coexistence of the legacy
`kubernetes/` root with the synced upstream application — not a defect in the
manifests, and not a regression of F1–F5.** It is also **not** a pass: the
legacy root does **not** server-dry-run cleanly on a cluster where the
upstream application is synced. Both facts are recorded; neither is rounded
away. **Owner for the coexistence decision: P03** (see §11).

## 3. F1–F5 — what was fixed and how it was proven

### F1 — client-side apply destroyed the Argo CD CRDs

**Before (reproduced on a clean kind cluster, 2026-10-20):**

```console
$ kubectl apply -n argocd -f <argo-cd install.yaml>       # client-side
...
The CustomResourceDefinition "applicationsets.argoproj.io" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes
RC=1
$ kubectl get crd | grep argoproj
applications.argoproj.io                    Namespaced   v1alpha1(storage)
appprojects.argoproj.io                    Namespaced   v1alpha1(storage)
                                                  # applicationsets.argoproj.io is MISSING
```

The ApplicationSet CRD was never created, the `&&` chain aborted the rest of
the install, and the ApplicationSet controller has no CRD to work with. The
cause is structural: a client-side apply stores the entire object in
`kubectl.kubernetes.io/last-applied-configuration`, and that CRD's schema is
larger than the 256 KiB annotation limit.

**Fix:** `scripts/bootstrap.sh` now applies the upstream manifest
**server-side**:

```console
$ kubectl apply -n argocd --server-side --force-conflicts \
    --field-manager=aks-sre-bootstrap -f "$ARGOCD_MANIFEST_URL"
```

The **whole** manifest goes server-side: measured on the same clean cluster,
every object (3 CRDs, StatefulSet, Deployments, Services, RBAC, ConfigMaps,
NetworkPolicies) applied with rc=0, so nothing had to fall back to
client-side apply. The repo-owned manifests in step 3/3 (the AppProject and
the Applications) stay **client-side** on purpose: they are far below the
annotation limit, and client-side apply computes a diff against the previous
configuration, so a key removed from a manifest in Git is removed from the
cluster. A server-side apply only removes fields the applying field manager
owns, which is a weaker contract for the object whose whole purpose is to be
the allowlist.

**After (full `bash scripts/bootstrap.sh` on a clean cluster):**

### 10.4 The conclusion — stated precisely, and bounded

> **Verified:** Argo CD **v3.5.5** does **not** include an *added*
> `metadata.labels` entry in the live-vs-desired diff. Such a label is
> therefore neither reported as `OutOfSync` nor reverted by `selfHeal`.
>
> **Verified (and positive):** drift that changes a **spec** field *is*
> detected and reverted in about **1 second** — the replica count was scaled
> to 1 at 16:43:22Z and Argo restored it at 16:43:24Z (§9.5 A); a deleted
> managed `Deployment` was re-created in about **1 second**
> (16:44:04Z → 16:44:05Z, §9.5 B).
>
> **NOT VERIFIED — and therefore not claimed:** self-heal for **extra metadata
> labels**. The label had to be removed by a human.
>
> **NOT VERIFIED:** drift in **any other metadata field** (`annotations`,
> `finalizers`, `ownerReferences`, …). Argo CD's diff of metadata is
> field-specific; this run probed **only** `metadata.labels`. Any claim that
> "Argo CD reverts metadata drift" would be false as written — the correct
> statement is the one above: **spec drift and resource deletion self-heal;
> extra metadata labels do not.**

**Scope of the finding.** It is a property of the Argo CD v3.5.5
live-vs-desired diff, **not** a defect in this repository's manifests, and
**not** a regression introduced by F1–F5. It is recorded because it changes
what "self-heal" means for an operator running this platform: a hand-applied
label on a managed resource is invisible to Argo CD.

**Operational consequence.** Any label that is meaningful to an operator
(e.g. a temporary "freeze" marker) is invisible to Argo CD and will survive
forever. Conversely, a label that *is* present in the desired manifest will be
re-applied if removed — but a label that is *not* in the desired manifest is
never reconciled. Both directions matter for change management.

**Not fixed in this run, on purpose.** Options exist (an Argo CD
`ignoreDifferences` rule — which would make it *worse*, not better — or a
periodic drift-reconciliation job). Neither was implemented: this run is
evidence-only, and an unrequested controller would be a bigger change than the
finding warrants. It is listed as an open item with an owner in §11.

> *A locally built `:local` image is pinned to the upstream revision it was

Full evidence: the recreate document **§6**.

## 13. Limits of reproduction — the kind cluster is a disposable artifact

**This section exists so that no reader mistakes this document for a durable
guarantee. It is not.**

1. **The kind cluster is disposable, and it was destroyed once during this
   day by another actor.** A blanket `docker rm -f` sweep by another actor on
   this machine removed the kind node containers; the cluster had to be
   recreated. Nothing in this repository can prevent that, because a kind
   cluster is just Docker containers on a shared daemon.

2. **Every runtime claim in this document is point-in-time.** "Application
   `flashsale` is `Synced`/`Healthy`" means *at the timestamp quoted in the
   row*, on *that* cluster instance, with *that* revision
   (`8adcbeff002b503f556f0e4fb7a892f8aeffae43`). It is not a property of the
   branch — the same branch, re-bootstrapped tomorrow, produces a fresh
   measurement and may legitimately differ.

3. **The measurements that survive a cluster loss are the repo-side ones** —
   the gates (policy-gate, GitOps validator, gate tests), the kustomize
   renders, the `terraform test` offline assertions, the manifest dry-run.
   Those are reproducible from the branch alone. The Kubernetes runtime rows
   are not.

4. **The host was not stable during the measurement window.** Docker Desktop
   crashed three times (§11 #6). Some of the pod restart counts in §2.1 are
   a property of the workstation, not of the manifests. Anyone re-running
   §12 should expect a *different* restart count and should not treat a
   different number as a regression — or as a pass.

5. **Recommendation — isolate the kind cluster from the rest of this
   machine.** The single highest-value change for the reliability of this
   evidence is to run the kind cluster in a **dedicated Docker context**
   (`docker context create platform --docker host=unix:///run/user/501/docker-platform.sock`)
   or, better, on a **dedicated VM / Lima / OrbStack VM** with its own
   disk and memory budget. That would:
   - stop another actor's `docker rm -f` / `docker compose down` from
     destroying the evidence cluster mid-measurement;
   - stop the load of a second kind cluster from starving the first (the
     14:14Z leader-election loss in §2.1 event 1);
   - stop the daemon restarts from being attributed to Argo CD pods
     (§2.1 event 2);
   - make the restart counts in a future run meaningful again.

   Until that exists, the restart counters on this host are not usable as a
   regression signal, and this document says so rather than publishing a
   flattering number.

### 15.6 The npm start bug, fixed and gated

**Found by the 2026-10-21 verification, reproduced first:**

```console
$ npm start                       # before the fix
> sre-demo-api@1.0.0 start
> node src/server.js
$ curl -s -o /dev/null -w "HTTP=%{http_code}\n" http://127.0.0.1:8080/health
HTTP=000
$ pgrep -fl "node src/server.js"
(no process — the script exited immediately)
```

`src/server.js` only **exports** `createServer`; it never calls `listen()`.
The real entrypoint is `src/index.js` (the composition root: metrics, logger,
state, server, `listen`, signal handling). The **Dockerfile** was already
correct — `CMD ["node", "src/index.js"]` — so the **image worked while the
npm script did not**, which is why the defect survived.

**Fix:** `app/sre-demo-api/package.json` → `"start": "node src/index.js"`.

**Verified after the fix:**

```console
$ npm ci
$ npm test
ℹ tests 7
ℹ pass 7
ℹ fail 0

$ PORT=18081 npm start
> sre-demo-api@1.0.0 start
> node src/index.js
{"timestamp":"2026-10-21T02:19:15.074Z","level":"info","service":"sre-demo-api","message":"sre-demo-api listening","port":18081,...}

$ curl -s -w "\nHTTP=%{http_code}\n" http://127.0.0.1:18081/health
{"status":"live","uptime_s":2.605}
HTTP=200
$ curl -s -o /dev/null -w "HTTP=%{http_code}\n" http://127.0.0.1:18081/health/live
HTTP=200
$ curl -s -o /dev/null -w "HTTP=%{http_code}\n" http://127.0.0.1:18081/health/ready

```

> **Do not verify this with a fixed short sleep.** The process needs ~3–4 s
> to become reachable (the OTel SDK is initialised before the server starts
> listening), so a `sleep 1; curl` can return `000` on a loaded host even
> though the fix is good. Poll instead:
>
> ```bash
> for i in $(seq 1 15); do sleep 2; \
>   [ "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:18081/health)" = 200 ] && break; done
> ```
>
> That loop reached `HTTP=200` after ~4 s on 2026-10-21.

> **Why `PORT=18081` and not the default `8080`.** On this machine
> `127.0.0.1:8080` is **already published by this repository's own kind node**
> (`local-platform-control-plane … 127.0.0.1:8080->30080/tcp`), so a request
